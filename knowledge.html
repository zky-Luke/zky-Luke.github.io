01 / FOUNDATION

LLM 应用：
不是聊天框 API

一个可用的 LLM 功能，至少要处理：输入意图、上下文、模型输出格式、流式状态、异常和成本。模型只是中间一环。

核心概念

Messages

系统指令决定边界；用户消息提供任务；历史消息提供上下文。不要把所有历史无限塞进去。

Streaming

边生成边展示，降低“等待感”；前端应支持取消、加载中与半截失败状态。

Structured output

让模型按 JSON Schema 输出，前端才能稳定地渲染卡片、表格或工作流。

一次请求的正确路径

用户输入→服务端校验→模型调用→解析/校验→UI 呈现

最小实现：服务端代理

API Key 永远只放服务端环境变量；浏览器只调用自己的 /api/chat。

// server route — 伪代码
const response = await client.chat({
  model: selectedModel,
  messages,
  stream: true,
});
return toTextStreamResponse(response);
常见坑：直接把 Key 写进前端；默认相信模型返回的 JSON；不允许用户停止生成；没有记录耗时、模型与 token。
动手验证

做一个流式聊天框：支持停止、错误提示、复制答案；日志中打印模型名、首字延迟和总耗时。

02 / RETRIEVAL

RAG：让回答
有根据

RAG 不是“上传文件后问答”。它是把外部知识检索出来，再作为受控上下文交给模型回答的工程管线。

完整链路

原始文档解析Chunk向量化检索重排序带引用回答

必须理解的 4 件事

  1. Chunk：按标题/段落切分比机械按字数更容易保留语义；Chunk 太大噪声多，太小上下文不够。
  2. Embedding：把文本映射到向量空间，用于找“语义相近”的内容，不是让模型记住文档。
  3. Hybrid search：语义检索擅长同义表达，关键词检索擅长专有名词；实际系统常组合两者。
  4. Rerank：先用便宜检索召回候选，再用更强模型重排，提升最终上下文质量。

RAG 的最小伪代码

const chunks = await vectorStore.search(question, { topK: 12 });
const context = await rerank(question, chunks).then(x => x.slice(0, 5));
const answer = await model.generate({
  prompt: `只依据以下资料回答；不知道就说不知道。\n${context}`
});
常见坑：没有来源引用；只测“回答好不好”却不测检索是否命中；遇到资料外问题时仍让模型猜。
动手验证

拿 10 篇自己的技术文档，写 20 个问题。记录“检索是否命中”和“引用是否正确”，再优化分块与 Top-K。

03 / ORCHESTRATION

Agent 与 MCP：
模型开始行动

Agent 是“模型 + 工具 + 状态 + 控制循环”。它适合需要分步骤、要调用外部系统的任务；简单问答不应硬上 Agent。

Agent Loop

目标→判断下一步→调用工具→读取结果↺

什么时候该用、什么时候别用

适合 Agent不适合 Agent
多步骤研究、调用多个工具、执行过程需根据结果调整固定表单处理、简单分类、单次知识库问答、要求绝对确定的流程

MCP 是什么

MCP（Model Context Protocol）是一套让 AI 客户端以统一方式连接外部工具和数据的协议。你可以把它理解为 AI 世界的“标准插件接口”：客户端发现工具，服务端暴露工具描述和执行能力。

// 一个好工具描述应包含
name: "search_docs"
input: { query: string, limit?: number }
description: "搜索已授权的内部文档，返回标题、摘要和来源链接。"
安全底线：工具权限最小化；涉及删除、发消息、付款等操作必须要求用户确认；不能让网页正文直接变成 Agent 指令。
动手验证

做一个研究助手：可搜索资料、读取单篇内容、最后生成带来源的结论；在 UI 展示每一步工具调用。

04 / SHIP

AI 全栈交付：
从 Demo 到产品

AI 产品的难点不是“能调模型”，而是稳定、成本、权限、可观测性和体验在真实用户面前仍然成立。

推荐架构

React / Next 前端→API 层：鉴权、限流、模型路由→LLM / Tools / RAG→DB + 日志 + 评测

上线前检查清单

  • 密钥只存在环境变量；前端不出现供应商 Key。
  • 流式、超时、取消、限流和模型失败都有用户可理解的状态。
  • 记录请求 ID、模型、耗时、成本、工具调用和错误。
  • 准备 20–50 条真实任务做回归评测；每次改 Prompt 或模型都跑一遍。
  • 先让 3 位真实用户完成任务，再决定下一个功能。
最终作品

做一个垂直 AI 小工具，写完整 Case Study：用户问题、架构图、模型选择、评测集、结果、失败案例与下一步。
